# Contributing

Thanks for improving gwnative. The project is macOS-specific and its runtime
boundary spans Rust, AppKit, WebKit, JavaScript, and WebAssembly, so changes
should be checked on Apple Silicon whenever possible.

## Before changing code

Read the documents that match the change:

- [Architecture](docs/architecture.md) for component boundaries and invariants
- [Development](docs/development.md) for setup, tests, and debugging
- [Performance](docs/performance.md) before changing a measured hot path
- [Release guide](docs/releasing.md) before changing packaging, signing, or CI

The source modules carry detailed rationale for local invariants. Keep that
rationale close to the implementation; keep workflows and cross-component
contracts in `docs/`.

## Quality checks

Run the same checks as CI:

```sh
scripts/check-docs
cargo deny check
cargo fmt --all --check
cargo clippy --all-targets -- -D warnings
cargo test
cargo build --release
scripts/bundle
```

`cargo deny check` requires
[`cargo-deny`](https://github.com/EmbarkStudios/cargo-deny). `cargo test` runs
the JavaScript tests through Node's built-in test runner when Node is installed.
It prints a skip notice otherwise. CI always has both tools.

For a documentation-only change, at minimum run `scripts/check-docs`.

## Repository-owned artifacts

- `web/Gw.jspi.js`, `web/Gw.jspi.wasm`, and `web/version.json` are live client
  artifacts. A sync can update them in a source checkout; inspect their diff
  before committing.
- `src/boot-chunks.json` is the built-in first-launch prefetch list.
- `packaging/AppIcon.icns` is generated by `scripts/icon` and committed.
- `packaging/sparkle/Sparkle.framework` is vendored at a pinned version. Follow
  [its update procedure](packaging/sparkle/README.md), including checksum and
  licence verification.
- `packaging/certs` contains public Apple intermediate certificates only. Never
  commit a signing identity, private key, notarization credential, or exported
  keychain.

## Documentation standard

The root README is an entry point, not the project manual. Put information in
the narrowest durable home:

- player behaviour in `docs/user-guide.md`;
- system contracts and rationale in `docs/architecture.md`;
- contributor commands in `docs/development.md`;
- measurements in `docs/performance.md`; and
- operational procedures in `docs/releasing.md`.

Commands must be runnable as written. Mark measurements with their environment
and date, distinguish observations from guarantees, and update both sides of a
contract when code changes. If player-facing behaviour changes, also update the
offline guide in `web/guide.js`.

## Pull requests

Keep changes focused, explain the user-visible outcome, and include the checks
you ran. Performance claims need before-and-after measurements from the same
machine and comparable cache state. Signing or release changes should be
exercised with the release workflow's dry-run path before publication.
